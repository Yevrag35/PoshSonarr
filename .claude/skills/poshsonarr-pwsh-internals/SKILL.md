# PowerShell internals for PoshSonarr

PoshSonarr is a binary module for PowerShell 7 alone: its manifest declares only the Core edition, and its cmdlet assemblies target `net10.0`. Its cmdlets are written in C#, and its models derive from `PSObject`, so how they receive input, report errors, stop, clean up, ship help, and load depends on details of the PowerShell engine that the documentation leaves out. This skill records those details as measured, with the PowerShell version and the date of each measurement.

- Trust a measurement here over recollection. When a change depends on a fact that a newer PowerShell release could change, measure it again.
- When you measure something that later work could depend on, add it to the reference it belongs to, with the version and the date, instead of saving it as a memory. Say what it means for PoshSonarr beside it, as a rule the code has to follow rather than a description of the code as it is today.
- When a measurement shows that the code breaks a rule, or exposes a bug, write down the rule that the code is meant to follow, not the bug, and report the bug.
- Don't point to working notes, such as review or bug lists, which may not stay in the repo. State the fact, the rule, or the reason itself.

## Measuring PowerShell behavior

- Measure on a stable PowerShell 7 release that can load the module, and record the version and the date with each result. Use a preview only to check whether a coming release changes a fact, and say so beside the result.
- Run each experiment in a new process, with `pwsh -NoProfile -NonInteractive -File ...` or `-Command ...`. A process that has loaded a build keeps its DLLs locked until it exits, and PowerShell 7 can't load two builds of the same assembly in one process.
- When an experiment imports the module, import the build by its path with `-ErrorAction Stop`, and check that the command comes from the build, with `(Get-Command Get-SonarrSeries).Module.Path`, before you trust a result. Otherwise an installed PoshSonarr, such as a release from the PowerShell Gallery, can answer instead: when the import fails, the next call auto-loads the installed module without an error.
- Importing `MG.Sonarr.Next.Shell.dll` by its path names the module after the DLL, exports every cmdlet in it, and processes none of the type and format files. When a result depends on the module's name, its exports, its help, or its type and format data, import a staged manifest instead.
- The cmdlets get their services from the connection that `Connect-SonarrInstance` makes. Without one, a cmdlet ends the statement in `BeginProcessing` with a `ContextNotSetException`, before any pipeline input binds, and a transformation attribute that creates a service scope fails the binding with that exception (measured 2026-10-25 on PowerShell 7.6.8). Named arguments bind and validate before `BeginProcessing`, so a parameter's validation can be measured without a Sonarr server. Pipeline binding needs a connection, or throwaway `Add-Type` types and cmdlets shaped like the module's, such as a `PSObject` subclass that calls `base(capacity)`.
- To pass an array to a script, use `-Command "& '<script>' -Path a, b"`. Under `-File`, `-Path a,b` arrives as the single string `'a,b'`.
- An experiment that needs the global scope, such as one that assigns a preference variable there, dot-sources its script from `-Command`, as in `-Command ". '<script>'"`. With `& '<script>'` and under `-File`, the script runs in a scope of its own.
- To see whether the binder prompts for a missing mandatory parameter, leave out `-NonInteractive` and pipe the answer into the new process, as in `'6' | pwsh -NoProfile -File <script>`. The console host reads the answer from stdin, and the call goes on with it. Under `-NonInteractive`, the same call fails with `MissingMandatoryParameter` instead of prompting.
- `Add-Type -OutputAssembly` doesn't replace a file. When the file exists, it reports that, leaves the old assembly in place, and doesn't stop the script, even under `-ErrorAction Stop`, so delete the old DLL before you compile again (seen 2026-10-25 on PowerShell 7.6.8).
- Give a scratch function a name that no alias has. An alias wins over a function, so a function named `h` runs `Get-History` instead, without an error (seen 2026-10-25 on PowerShell 7.6.8).
- In script, `$psObject.BaseObject` reads a member of the wrapped object, which is usually `$null`, so use `$psObject.psobject.BaseObject`. `$model.psobject` is a member set, not the model, so compare instances by the variables themselves, with `[object]::ReferenceEquals($a, $b)`, and get a model's class from C#, because `$model.GetType()` reports `PSCustomObject`.
- Pester runs each test inside a `try` block, where an error that ends a statement and one that ends the script both jump to `catch`. To see how an error ends a script, run it in a new process, outside any `try` block. A `PipelineStoppedException` skips `catch` blocks and runs `finally` blocks, so read what it left behind in a `finally` block.
- When an experiment or a test should show that a change makes a difference, also run it against the build from before the change, and check that the difference shows.
