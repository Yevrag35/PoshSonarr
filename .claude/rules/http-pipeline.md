# HTTP pipeline

Every request the module makes to Sonarr's API goes through `ISonarrClient`, which `SonarrHttpClient` implements in `src/MG.Sonarr.Next/Services/Http/Clients/`. The client builds a request message, sends it through a chain of delegating handlers, and has `IResponseReader` turn the response into a `SonarrClientResult` or `SonarrClientResult<T>`. No exception leaves the client: a failure comes back as a result whose `IsError` is `true` and whose `Error` is a `SonarrErrorRecord`.

## Registration

`SonarrClientDependencyInjection`, at the bottom of `SonarrHttpClient.cs`, registers the client. `SonarrContext.Build` in `src/MG.Sonarr.Next.Shell.Bases/Context/CmdletContext.cs` calls `AddSonarrClient` once per connection, and once per `Test-SonarrHost` call, whose provider the cmdlet disposes when its test ends.

- `AddHttpClient<ISonarrClient, SonarrHttpClient>` makes the client a typed client of `IHttpClientFactory`. Its `HttpClient` takes `IConnectionSettings.ServiceUri` as the base address and `IConnectionSettings.Timeout` as the timeout, and sends the API key in the `X-Api-Key` header and `PoshSonarr-Next/2.0.0` as the user agent on every request.
- `HttpClient` takes a timeout greater than zero and at most `int.MaxValue` milliseconds, about 24.8 days, or `Timeout.InfiniteTimeSpan`, and throws an `ArgumentOutOfRangeException` for any other value while the client is built, each time a scope resolves `ISonarrClient` (measured 2026-10-30 on .NET 10.0.14). So the `-Timeout` of `Connect-SonarrInstance` and of `Test-SonarrHost` carries `[ValidateTimeout]`, which turns away such a value, and the infinite one too, when the arguments bind. Its error names the value, since PowerShell reads a number as ticks and a string such as `'30'` as days.
- `ISonarrClient` resolves as a transient, with a new `HttpClient` each time, but the factory reuses one handler chain until its handler lifetime runs out, two minutes by default. A handler that needs `IConnectionSettings` reads it in its constructor, so it sees the settings as they were when its chain was built. Every request and cmdlet in that window shares the chain, so a handler keeps no per-request or per-cmdlet state in its fields.
- `ISonarrClient` and `ISonarrDownloadClient` take the scoped `ApiCmdletAccessor`, so code resolves them from a scope, as every cmdlet does. Resolving one from the root provider throws an `InvalidOperationException` while the container validates scopes, as it does in builds other than Release (measured 2026-10-29 with Microsoft.Extensions.DependencyInjection 10.0.14).
- The same registration adds the metadata tags, the singleton `IResponseReader`, the `IConnectionSettings` instance, the singleton `CookieContainer` that every `SonarrClientHandler` of the connection shares, the scoped `ApiCmdletAccessor` that holds a scope's cmdlet, `ISonarrJsonOptions`, and the download client.
- `AddSonarrNonPSClient` registers the client for a host outside PowerShell, with only `PathHandler` and `TestingHandler` in its chain.
- A new delegating handler is registered as a transient beside the others and added with `AddHttpMessageHandler<T>()` at its place in the chain.

## Handler chain

`AddSonarrClient` adds the handlers in this order. The first one added is the outermost: it sees the request first and the response last.

1. `PathHandler` builds the request's URL from the scheme and server, the URL base, and the endpoint path prefixed with `/api/v3/`, or with `/v3/` when `-NoApiInPath` sets `IConnectionSettings.NoApiInPath`. The URL base is the path of `IConnectionSettings.ServiceUri` without its trailing slash, such as `/sonarr` for `-Url https://host/sonarr/`, and it's empty for a URL without a path. Callers pass the path relative to the API and rooted, as the paths in `Constants` are, such as `/series` or `/system/status`, so the combination with the base address that `HttpClient` makes keeps only the address's scheme and server. A path that already starts with `api/v3`, and a request whose options hold the `PathHandler.Ping` key, get the URL base without the prefix. The handler leaves alone a path that already starts with the URL base and `api/v3`, and an `AuthedRequestMessage`. The path and query keep the escaping the caller gave them.
2. `VerboseHandler` reads the cmdlet that sent the request from the request's options, with `ApiCmdletAccessor.TryGetCmdlet`. When the cmdlet's `CanWriteVerbose` is `true`, the handler calls its `WriteVerboseBefore` with the request before sending it, and its `WriteVerboseAfter` with a result that holds the response's status code and URL afterward.
3. `DebugSerializeHandler` reads the cmdlet from the request's options and writes payloads to its debug output through `WriteDebugPayload`: the request body before sending, as `HTTP Request (size in bytes: <length>) -> <body>`, when `CanDebugSerializeBefore` is `true`, and the response body after receiving, as `HTTP Response (size in bytes: <length>) -> <body>`, when `CanDebugSerializeAfter` is `true`. A cmdlet that writes its request body to the debug stream itself, through `SonarrCmdletBase.SerializeIfDebug`, overrides `CanDebugSerializeBefore` to return `false`, so the body appears once.
4. `TestingHandler` buffers every request body with `HttpContent.LoadIntoBufferAsync`, which gives the request a `Content-Length` header, where a `JsonContent` body that isn't buffered goes out chunked (measured 2026-10-28 on .NET 10.0.14). It acts on the response only for a request whose `SonarrRequestMessage.IsTest` is `true`, the `TestRequestMessage` that `SendTest` sends. `/system/status` always answers with a JSON object, so when that request succeeds with a body whose first byte, past a UTF-8 byte order mark and JSON whitespace, isn't `{`, the URL doesn't point at Sonarr's API, and the handler disposes the response and returns a 503 whose JSON body's `message` says so. Otherwise it puts the buffered body back.
5. `ErrorHandler` acts on a non-success response. A 404 passes through unchanged, with the `ErrorHandler.Is404` key added to its request's options for the response reader. Any other error response with a JSON content type has its body buffered, and a body that is one JSON object is parsed into a server error, which goes into the request's options under `ErrorHandler.ErrorKey`. Whatever the body holds, one error object, the array of validation failures that Sonarr returns for a 400, or JSON that doesn't parse, the response reaches the response reader with its body and content headers intact.

`SonarrClientHandler`, the primary handler, sends through the proxy from `IConnectionSettings.TryGetProxy`, or answers a server's authentication challenge with the user's default credentials when there's no proxy. It accepts any server certificate when `-SkipCertificateCheck` sets `IConnectionSettings.SkipCertValidation`. It follows redirects, and it keeps cookies in the connection's singleton `CookieContainer`, so a cookie that one primary handler received goes out with the requests that the others send.

A delegating handler follows these rules:

- It overrides both `Send` and `SendAsync`. The synchronous client methods send with `HttpClient.Send`, which calls each handler's `Send`, and `DelegatingHandler.Send` passes the request to the inner handler without calling the handler's own `SendAsync`, so a handler that overrides only `SendAsync` is skipped on that path (measured 2026-10-25 on .NET 10.0.14). A handler with no synchronous logic of its own implements `Send` as `this.SendAsync(request, cancellationToken).GetAwaiter().GetResult()`.
- When it reads a response body, it puts a buffered copy back as the response's content, with the original content headers copied over by `HttpContentHeaderExtensions.CopyTo`, so the handlers outside it and the response reader can read the body again. When it reads a request body, it buffers the content with `LoadIntoBufferAsync` first, and the primary handler then sends the body from that buffer.
- Flags for one request travel in the request's `Options`. `HttpResponseMetadataExtensions` reads and writes them from a response, through its `RequestMessage`.

## Request messages

Every request is a `SonarrRequestMessage`, from `src/MG.Sonarr.Next/Services/Http/Requests/`.

- It keeps the path the caller passed as `OriginalRequestUri`, and it opens a DI scope that it disposes with itself. As an `IHttpRequestDetails`, it gives `WriteVerboseBefore` the method, the URL, and that scope's services.
- `ApiKeyRequestMessage` carries API calls, `TestRequestMessage` carries `SendTest`, and `AuthedRequestMessage` carries a download that may need credentials.
- A request message, with its content and its scope, stays alive until the response has been read, so a method that disposes its request with `using` awaits the send first. In a method that returns the send's `Task` without awaiting it, `using` disposes the request when the method returns, while the request is still in flight, and a handler that reads the body after that throws `ObjectDisposedException` (measured 2026-10-25 on .NET 10.0.14).

## SonarrHttpClient

`SonarrHttpClient.cs` holds the type's fields, its constructor, its synchronous methods, and the registration class, and `SonarrHttpClient-Async.cs` holds its asynchronous methods. `ISonarrClient` is split the same way, with each member declared in the file that implements it.

- The constructor takes the typed `HttpClient`, `IConnectionSettings`, `ISonarrJsonOptions`, `IMetadataResolver`, `IResponseReader`, the scope's `ApiCmdletAccessor`, and the `IServiceScopeFactory` that each request message opens its scope from.
- `SendDelete`, `SendGet<T>`, `SendPost`, and `SendPut`, each with an `Async` twin, create an `ApiKeyRequestMessage` for the relative path, serialize a body as JSON with `ISonarrJsonOptions.ForSerializing`, put the scope's cmdlet in the request's options, send the request, and hand an `HttpCall` (the path, the request, and the response) to `IResponseReader`: `ReadNoResultAsync` for the methods that return no data, and `ReadResultAsync<T>` for the rest.
- The response is disposed before the method returns, so the reader takes what the result needs from it first. A `SonarrHttpException` in an error result still holds that response in `Response`, so code that reads the error later uses the exception's own `StatusCode`, `ReasonPhrase`, and `Headers`, which it copied, and never the response's content.
- `SendGet<T>` and `SendPost<TBody, TOutput>` set the metadata tag on a value that is `IJsonMetadataTaggable`, with `SetTag(IMetadataResolver)`. `SendGet<T>` also sorts a value that is `ISortable` and holds more than one item.
- An exception becomes an error result. A timeout, which `HttpClient` reports as a `TaskCanceledException` whose inner exception is a `TimeoutException`, gets the category `OperationTimeout`, and any other cancellation gets `OperationStopped`. An `HttpRequestException` is wrapped in a `SonarrHttpException`, along with any server error parsed from the response. When the exception gives no request URL, the result's `RequestUrl` falls back to the relative path.
- `SendTest<T>` is how `Connect-SonarrInstance` and `Test-SonarrHost` check the URL and API key. It sends `GET /system/status` as a `TestRequestMessage`, and on success it reads the status as `T` through `IResponseReader` and tags it. An error status becomes an `HttpResponseException` with the category `ResourceUnavailable`, the response's status code, such as the 401 for a wrong key or the 503 from `TestingHandler`, and the request's URL as the record's target. Its message is the `message` from the JSON body, or the status code as `ToResponseString` writes it, such as `401 (Unauthorized)`, when the body is empty, as Sonarr's 401 is, isn't JSON, or has no `message`. An exception, such as a refused connection, becomes a `ConnectionError` with the response's status code, or 599 when there's no response. `SendTest` calls `SendTest<SonarrStatus>` and stores the server's authentication type from the status in `IConnectionSettings.AuthType`. With `-PassThru`, `Connect-SonarrInstance` calls `SendTest<SystemStatusObject>` instead, so it fails in the same way, and it writes the status out and stores the authentication type itself. `Test-SonarrHost` calls `SendTest<SystemStatusObject>` too.
- `SendPingAsync` sends `HEAD /ping` with the `PathHandler.Ping` key in its options, so the path gets the URL base but no API prefix. It turns a 404, 403, 401, or 5xx response into `ObjectNotFound`, `PermissionDenied`, `AuthenticationError`, or `ConnectionError`, and any other failure into `InvalidResult`.
- The `Send*Request` helpers on `SonarrApiCmdletBase` call the asynchronous methods and block on them with `GetAwaiter().GetResult()`. `SendTest`, `CommandTracker`, and `TestingService` use the synchronous ones. Both kinds run through the same handlers.

## Response reader

`SonarrResponseReader`, the singleton `IResponseReader`, turns an `HttpCall` into a result.

- A call with no response becomes an `EmptyHttpResponseException` error with the category `InvalidResult`.
- In `ReadResultAsync<T>`, a request marked with `ErrorHandler.Is404` becomes `SonarrClientResult.NotFound<T>()`, an ignorable `ObjectNotFound` error with the status 404.
- A status below 400 is a success. `ReadResultAsync<T>` deserializes the body as `T` with `ISonarrJsonOptions.ForDeserializing`, and a body that is `null` or can't be deserialized becomes a `ParserError` error.
- Any other status becomes a `SonarrHttpException` that holds the server's errors, read from a body that is one error object or an array of them, such as Sonarr's validation failures. A `SonarrErrorRecord` wraps it, with the category that `SonarrErrorRecord.GetCategoryFromStatusCode` picks for the status code, such as `InvalidData` for 400, `AuthenticationError` for 401 and 403, and `ObjectNotFound` for 404, which also makes the record ignorable.

A result carries `StatusCode`, `RequestUrl`, `IsError`, and `Error`, and `SonarrClientResult<T>` adds `Value`, which isn't `null` when `IsError` is `false`. `IsIgnoreable` is `true` for a status below 400 and for 404. A result that `SonarrClientResult.FromException` builds takes the status code its caller passes, which is `ErrorHandler.NoResponseCode`, 600, when there's no response, except in `SendTest`, which passes 599. The overload of `FromException<T>` for a `SonarrHttpException`, which the other generic overload hands such an exception to, takes the exception's status code instead, and 600 when the exception has none.

## The sending cmdlet

The handlers reach the cmdlet that sent a request, an `IApiCmdlet`, through the request's options, where the client that sends the request puts it.

- Every cmdlet runs in a DI scope of its own, and the container gives each scope one `ApiCmdletAccessor`, in `src/MG.Sonarr.Next/Services/Http/`. `CmdletContextExtensions.CreateScope` and `SetContext`, which create the scopes of `SonarrCmdletBase` cmdlets and of `Connect-SonarrInstance`, set the accessor's `Cmdlet` to the cmdlet when it's an `IApiCmdlet`, and leave it `null` otherwise.
- `SonarrHttpClient` and `SonarrDownloadClient` take the accessor of the scope that resolves them, and each of their methods calls `AttachTo` before it sends, which stores the cmdlet in the request's options. The handlers read it back with `ApiCmdletAccessor.TryGetCmdlet`. The scoped `CommandTracker` and `TestingService` resolve the client from the same scope, so their requests reach the cmdlet too, and a request from a scope without a cmdlet, such as one that `Get-SonarrCommandHistory` sends, writes no verbose or debug output.
- Each request carries the cmdlet of the scope that sent it, so cmdlets that run at once, as in the runspaces of `ForEach-Object -Parallel` or in thread jobs, each get the output of their own requests only.
- `TimedCmdlet.WriteVerboseAfter` reports the time since the cmdlet last started its timer. The `Send*Request` helpers on `SonarrApiCmdletBase` start it, and a `TimedCmdlet` that calls a client or a service itself, as `Test-SonarrResource` and `Invoke-SonarrRssSync` do, starts it before each request.
- A handler calls `WriteVerboseAfter` and `WriteDebugPayload` after an `await`, often on a thread-pool thread, so an `IApiCmdlet` writes through `Host.UI.WriteVerboseLine` and `Host.UI.WriteDebugLine`. Off the pipeline thread, `Cmdlet.WriteVerbose` throws a `PSInvalidOperationException`, and a line written through `Host.UI` goes straight to the host, so `4>$null` doesn't hide it and `4>&1` doesn't capture it (measured 2026-10-25 on PowerShell 7.6.9).

## Download client

`ISonarrDownloadClient`, in `SonarrDownloadClient.cs`, saves a file that Sonarr serves, such as a backup or a log file, to a path. `AddSonarrClient` registers it as well.

- Its handler chain is `VerboseHandler`, `DebugSerializeHandler`, and `AuthHandler`, in that order, in front of `SonarrClientHandler`. It has no `PathHandler`, so the client itself puts the URL base in front of a relative download URL, unless the URL starts with the base already, in any case. Sonarr gives a backup's `path` without the URL base and a log file's `downloadUrl` with it, and Sonarr v3 lowercases the base (read in Sonarr's source on its `v3` and `main` branches, 2026-10-29). The URL that results is rooted, so combining it with the base address keeps only the address's scheme and server, and an absolute URL goes out unchanged.
- A response whose status isn't a success becomes an error result, whose `SonarrHttpException` says that the server didn't return the file, and the client writes nothing, since the body of such a response, often an HTML page, isn't the file.
- `AuthHandler` adds credentials when `IConnectionSettings.AuthType` says the server needs them, which `SendTest`, or `Connect-SonarrInstance -PassThru`, stored. It takes them from an `AuthedRequestMessage`, which the download overload with a `NetworkCredential` sends, and without them, or when a login fails, the download fails with a `SonarrHttpException`.
	- For Basic authentication, it adds an `Authorization: Basic` header, encoded in a stack or pooled buffer that it clears afterward.
	- For forms authentication, it posts the credentials to the login page under the URL base, `<base>/login?returnUrl=<base>/`. The primary handler follows the redirect that answers the login, which lands on a URL with `loginFailed=true` when the credentials are wrong, and keeps the login's cookie in the shared `CookieContainer`, which adds it to every later request. The handler logs in only when the container holds no cookie for the request's URL, and when Sonarr answers a request with a 401 or sends it to the login page, it logs in again and resends the request once, to its original URL.
