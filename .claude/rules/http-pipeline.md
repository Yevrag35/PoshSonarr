# HTTP pipeline

Every request the module makes to Sonarr's API goes through `ISonarrClient`, which `SonarrHttpClient` implements in `src/MG.Sonarr.Next/Services/Http/Clients/`. The client builds a request message, sends it through a chain of delegating handlers, and has `IResponseReader` turn the response into a `SonarrClientResult` or `SonarrClientResult<T>`. No failure leaves the client as an exception: a failure comes back as a result whose `IsError` is `true` and whose `Error` is a `SonarrErrorRecord`. Only a `PipelineStoppedException` from the sending cmdlet's own output passes through.

## Registration

`SonarrClientDependencyInjection`, at the bottom of `SonarrHttpClient.cs`, registers the client. `SonarrContext.Build` in `src/MG.Sonarr.Next.Shell.Bases/Context/CmdletContext.cs` calls `AddSonarrClient` once per connection, and once per `Test-SonarrHost` call, whose provider the cmdlet disposes when its test ends.

- `AddHttpClient<ISonarrClient, SonarrHttpClient>` makes the client a typed client of `IHttpClientFactory`. Its `HttpClient` takes `IConnectionSettings.ServiceUri` as the base address and `IConnectionSettings.Timeout` as the timeout, and sends the API key in the `X-Api-Key` header and `PoshSonarr-Next/3.0.0` as the user agent on every request.
- `HttpClient` takes a timeout greater than zero and at most `int.MaxValue` milliseconds, about 24.8 days, or `Timeout.InfiniteTimeSpan`, and throws an `ArgumentOutOfRangeException` for any other value while the client is built, each time a scope resolves `ISonarrClient` (measured 2026-10-30 on .NET 10.0.14). So the `-Timeout` of `Connect-SonarrInstance` and of `Test-SonarrHost` carries `[ValidateTimeout]`, which turns away such a value, and the infinite one too, when the arguments bind. Its error names the value, since PowerShell reads a number as ticks and a string such as `'30'` as days.
- `ISonarrClient` resolves as a transient, with a new `HttpClient` each time, but the factory reuses one handler chain until its handler lifetime runs out, two minutes by default. A handler that needs `IConnectionSettings` reads it in its constructor, so it sees the settings as they were when its chain was built. Every request and cmdlet in that window shares the chain, so a handler keeps no per-request or per-cmdlet state in its fields.
- `ISonarrClient` and `ISonarrDownloadClient` take the scoped `ApiCmdletAccessor`, so code resolves them from a scope, as every cmdlet does. Resolving one from the root provider throws an `InvalidOperationException` while the container validates scopes, as it does in builds other than Release (measured 2026-10-29 with Microsoft.Extensions.DependencyInjection 10.0.14).
- The same registration adds the metadata tags, the singleton `IResponseReader`, the `IConnectionSettings` instance, the singleton `CookieContainer` that every primary handler of the connection shares, the scoped `ApiCmdletAccessor` that holds a scope's cmdlet, `ISonarrJsonOptions`, and the download client.
- `AddSonarrNonPSClient` registers the client for a host outside PowerShell, with only `PathHandler` and `TestingHandler` in its chain. It also registers `VerboseHandler` and `DebugSerializeHandler` for the download client that both registrations add, which write nothing for a request from a scope without a cmdlet, so every service it registers resolves.
- A new delegating handler is registered as a transient beside the others and added with `AddHttpMessageHandler<T>()` at its place in the chain.
- A handler that the module doesn't own, such as one that a package's extension method on `IHttpClientBuilder` adds, can't derive from `SynchronousHandler`, so it joins a chain only when it overrides `Send` itself. `DelegatingHandler.Send` passes a request to the inner handler without running a handler that overrides only `SendAsync`, and without an error. A package that ships only a netstandard2.0 build can't override `Send` at all, since .NET 5 added it. Check one before adding it: on its type, `GetMethod("Send", BindingFlags.Instance | BindingFlags.NonPublic, [typeof(HttpRequestMessage), typeof(CancellationToken)])` returns a method whose `DeclaringType` is `DelegatingHandler` when nothing overrides `Send` (measured 2026-11-16 on .NET 11.0.0).

## Handler chain

`AddSonarrClient` adds the handlers in this order. The first one added is the outermost: it sees the request first and the response last.

1. `PathHandler` builds the request's URL from the scheme and server, the URL base, and the endpoint path prefixed with `/api/v3/`, or with `/v3/` when `-NoApiInPath` sets `IConnectionSettings.NoApiInPath`. The URL base is the path of `IConnectionSettings.ServiceUri` without its trailing slash, such as `/sonarr` for `-Url https://host/sonarr/`, and it's empty for a URL without a path. Callers pass the path relative to the API and rooted, as the paths in `Constants` are, such as `/series` or `/system/status`, so the combination with the base address that `HttpClient` makes keeps only the address's scheme and server. A path that already starts with `api/v3`, and a request whose options hold the `PathHandler.Ping` key, get the URL base without the prefix. The handler leaves alone a path that already starts with the URL base and `api/v3`, and an `AuthedRequestMessage`. The path and query keep the escaping the caller gave them.
2. `VerboseHandler` reads the cmdlet that sent the request from the request's options, with `ApiCmdletAccessor.TryGetCmdlet`. When the cmdlet's `CanWriteVerbose` is `true`, the handler calls its `WriteVerboseBefore` with the request before sending it, and its `WriteVerboseAfter` with a result that holds the response's status code and URL afterward.
3. `DebugSerializeHandler` reads the cmdlet from the request's options and writes payloads to its debug output through `WriteDebugPayload`: the request body before sending, as `HTTP Request (size in bytes: <length>) -> <body>`, when `CanDebugSerializeBefore` is `true`, and the response body after receiving, as `HTTP Response (size in bytes: <length>) -> <body>`, when `CanDebugSerializeAfter` is `true`. A cmdlet that writes its request body to the debug stream itself, through `SonarrCmdletBase.SerializeIfDebug`, overrides `CanDebugSerializeBefore` to return `false`, so the body appears once. `SerializeIfDebug` writes the object by its runtime type with `ISonarrJsonOptions.ForDebugging`, which matches `ForSerializing` but indents, so it shows the body that goes out. Serializing a model runs its `OnSerializing`, which only the `Commit` or `Reset` after a request undoes, so a cmdlet calls it for a model inside its `ShouldProcess` block, where `-WhatIf` doesn't reach.
4. `TestingHandler` puts a buffered copy, with a `Content-Length` header, in place of every request body whose length isn't known, since a `JsonContent` body that isn't buffered goes out chunked (measured 2026-10-28 on .NET 10.0.14). It acts on the response only for a request whose `SonarrRequestMessage.IsTest` is `true`, the `TestRequestMessage` that `SendTest` sends. `/system/status` always answers with a JSON object, so when that request succeeds with a body whose first byte, past a UTF-8 byte order mark and JSON whitespace, isn't `{`, the URL doesn't point at Sonarr's API, and the handler disposes the response and returns a 503 whose JSON body's `message` says so. Otherwise it puts the buffered body back.
5. `ErrorHandler` acts on a non-success response. A 404 passes through unchanged, with the `ErrorHandler.Is404` key added to its request's options for the response reader. Any other error response with a JSON content type has its body buffered, and a body that is one JSON object is parsed into a server error, which goes into the request's options under `ErrorHandler.ErrorKey`. Whatever the body holds, one error object, the array of validation failures that Sonarr returns for a 400, or JSON that doesn't parse, the response reaches the response reader with its body and content headers intact.

The primary handler is a `SocketsHttpHandler`, which both clients' registrations set up with `UseSocketsHttpHandler(SonarrClientHandler.Configure)`. `SocketsHttpHandler` is sealed, so `SonarrClientHandler` is a static class that configures one rather than a handler of its own. The primary handler sends through the proxy from `IConnectionSettings.TryGetProxy`, or answers a server's authentication challenge with the user's default credentials when there's no proxy. It accepts any server certificate when `-SkipCertificateCheck` sets `IConnectionSettings.SkipCertValidation`. It follows redirects, and it keeps cookies in the connection's singleton `CookieContainer`, so a cookie that one primary handler received goes out with the requests that the others send. Its `MaxResponseDrainSize` is 0, so a response that's disposed before its body has been read to the end closes its connection instead of draining the rest of the body. A canceled token or a timeout ends a synchronous body read by disposing the response, and the read ends only when the connection closes: through the module's registration, against a loopback server that stopped a body after its headers, a cancellation at 300 ms returned after 2,317 ms with `HttpClientHandler`'s default drain and after 303 ms with none (measured 2026-11-16 on .NET 11.0.0).

A delegating handler follows these rules:

- It derives from `SynchronousHandler`, overrides `Send` only, and never awaits or blocks on a task. The clients send every request with `HttpClient.Send`, which calls each handler's `Send`, and `DelegatingHandler.Send` passes the request to the inner handler without calling the handler's own `SendAsync`, so code in a `SendAsync` override never runs for the module's requests (measured 2026-10-25 on .NET 10.0.14). `DelegatingHandler.SendAsync` passes a request on the same way, past a handler that overrides only `Send` and without an error (measured 2026-11-16 on .NET 11.0.0), so `SynchronousHandler` seals `SendAsync` to throw a `NotSupportedException` that names the handler, and a request sent with `HttpClient.SendAsync` fails instead of skipping every handler.
- It reads a body with the synchronous helpers in `HttpBodyExtensions`. A synchronous read takes no token, so each helper disposes the content when the request's token is canceled, which ends a read that waits on the server.
- When it reads a response body, it puts a buffered copy back as the response's content, with the original content headers copied over by `HttpContentHeaderExtensions.CopyTo`, so the handlers outside it and the response reader can read the body again. When it reads a request body, it calls `BufferContent`, which puts a pooled copy of the body in place of the request's content, with the original content headers and a `Content-Length` header, and returns the buffer. It reads that buffer without moving its position, since `StreamContent`'s first send starts at its stream's position (measured 2026-11-16 on .NET 11.0.0), and the primary handler then sends the body from the buffer.
- When code after the inner handler's `Send` throws, as the cmdlet's own verbose or debug output does under a `Stop` preference, it disposes the response before the exception leaves it.
- Flags for one request travel in the request's `Options`. `HttpResponseMetadataExtensions` reads and writes them from a response, through its `RequestMessage`.

## Request messages

Every request is a `SonarrRequestMessage`, from `src/MG.Sonarr.Next/Services/Http/Requests/`.

- It keeps the path the caller passed as `OriginalRequestUri`, and it opens a DI scope that it disposes with itself. As an `IHttpRequestDetails`, it gives `WriteVerboseBefore` the method, the URL, and that scope's services.
- `ApiKeyRequestMessage` carries API calls, `TestRequestMessage` carries `SendTest`, and `AuthedRequestMessage` carries a download that may need credentials.
- A request message, with its content and its scope, stays alive until the response has been read: each client method disposes its request with `using`, and it sends the request and reads the response before it returns.

## SonarrHttpClient

`SonarrHttpClient.cs` holds `ISonarrClient`, the class, and the registration class. Each method sends its request synchronously and returns once the response has been read, so the handlers run on the calling thread.

- The constructor takes the typed `HttpClient`, `IConnectionSettings`, `ISonarrJsonOptions`, `IMetadataResolver`, `IResponseReader`, the scope's `ApiCmdletAccessor`, and the `IServiceScopeFactory` that each request message opens its scope from.
- `SendDelete`, `SendGet<T>`, `SendPost`, and `SendPut` create an `ApiKeyRequestMessage` for the relative path, serialize a body as JSON with `ISonarrJsonOptions.ForSerializing`, put the scope's cmdlet in the request's options, send the request, and hand an `HttpCall` (the path, the request, and the response) to `IResponseReader`: `ReadNoResult` for the methods that return no data, and `ReadResult<T>` for the rest.
- The response is disposed before the method returns, so the reader takes what the result needs from it first. A `SonarrHttpException` in an error result still holds that response in `Response`, so code that reads the error later uses the exception's own `StatusCode`, `ReasonPhrase`, and `Headers`, which it copied, and never the response's content.
- A body is an `object`, and each method sends it as a `JsonContent` created with `body.GetType()`, so it's serialized by its runtime type. A body often arrives as an interface, such as the `ITagPipeable` values that `Add-SonarrTag` and `Clear-SonarrTag` send, and each `SonarrObjectConverter<T>` claims only its exact model type, so serializing by the type the caller holds would miss the model's converter. A type parameter on these methods names the response's type only.
- `SendGet<T>` and `SendPost<TOutput>` with a body set the metadata tag on a value that is `IJsonMetadataTaggable`, with `SetTag(IMetadataResolver)`. `SendGet<T>` also sorts a value that is `ISortable` and holds more than one item.
- An exception becomes an error result, the same way for the methods that return a value and those that don't. A timeout, which `HttpClient` reports as a `TaskCanceledException` whose inner exception is a `TimeoutException`, gets the category `OperationTimeout`, and any other `OperationCanceledException` gets `OperationStopped`. An `HttpRequestException`, which `HttpClient` throws when no response arrives, as for a refused or dropped connection, is wrapped in a `SonarrHttpException`, along with any server error parsed from the response, and gets `ConnectionError`, or `InvalidResult` when it comes with a response. A body that doesn't parse gives no server error, in every build. Any other exception gets `ConnectionError`, except a `PipelineStoppedException`, which isn't a failed request and leaves the client as it is: the sending cmdlet's own verbose or debug output throws one under a `Stop` preference, or when the user halts the cmdlet at an `Inquire` prompt, to end the cmdlet's pipeline. The result's `RequestUrl` is the request's absolute URL when the exception or the response gives it, as a `SonarrHttpException` always does, and the relative path otherwise.
- `SendTest<T>` is how `Connect-SonarrInstance` and `Test-SonarrHost` check the URL and API key. It sends `GET /system/status` as a `TestRequestMessage`, and on success it reads the status as `T` through `IResponseReader` and tags it. An error status becomes an `HttpResponseException` with the category `ResourceUnavailable`, the response's status code, such as the 401 for a wrong key or the 503 from `TestingHandler`, and the request's URL as the record's target. Its message is the `message` from the JSON body, or the status code as `AsResponseString` gives it, such as `401 (Unauthorized)`, when the body is empty, as Sonarr's 401 is, isn't JSON, or has no `message`. An exception, such as a refused connection, becomes a `ConnectionError` with the response's status code, or `ErrorHandler.NoResponseCode`, 600, when there's no response. `SendTest` calls `SendTest<SonarrStatus>` and stores the server's authentication type and URL base from the status in `IConnectionSettings.AuthType` and `IConnectionSettings.ServerUrlBase`. With `-PassThru`, `Connect-SonarrInstance` calls `SendTest<SystemStatusObject>` instead, so it fails in the same way, and it writes the status out and stores both itself. `Test-SonarrHost` calls `SendTest<SystemStatusObject>` too.
- `SendPing` sends `HEAD /ping` with the `PathHandler.Ping` key in its options, so the path gets the URL base but no API prefix. It turns a 404, 403, 401, or 5xx response into `ObjectNotFound`, `PermissionDenied`, `AuthenticationError`, or `ConnectionError`, and any other error status into `InvalidResult`. With no response, it gives `ConnectionError`, `OperationTimeout` for a timeout, and `OperationStopped` for a cancellation.
- The `Send*Request` helpers on `SonarrApiCmdletBase` call these methods. Unless a caller passes a token that can be canceled, they send with the cmdlet's `PipelineStopToken`, which PowerShell cancels when the pipeline is stopped, so Ctrl+C ends a request in flight and the client reports it as `OperationStopped`. A cmdlet that calls a client or a service itself, such as `SendTest`, the download client, `CommandTracker`, or `TestingService`, passes its `PipelineStopToken` too.

## Response reader

`SonarrResponseReader`, the singleton `IResponseReader`, turns an `HttpCall` into a result.

- A call with no response becomes an `EmptyHttpResponseException` error with the category `InvalidResult`.
- In `ReadResult<T>`, a request marked with `ErrorHandler.Is404` becomes `SonarrClientResult.NotFound<T>(url, target)`, an ignorable `ObjectNotFound` error with the status 404, whose record is new for each call and carries the request's URL and the reader's target, since PowerShell's `WriteError` stores where a record was written in the record itself.
- A status below 400 is a success. `ReadResult<T>` deserializes the body as `T` with `ISonarrJsonOptions.ForDeserializing`, and a body that is `null` or can't be deserialized becomes a `ParserError` error with the request's URL. A cancellation while the body is read propagates as an `OperationCanceledException`, which the client reports as `OperationStopped`.
- Any other status becomes a `SonarrHttpException` that holds the server's errors, read from a body that is one error object or an array of them, such as Sonarr's validation failures, and none, in every build, from a body that doesn't parse. A `SonarrErrorRecord` wraps it, with the category that `SonarrErrorRecord.GetCategoryFromStatusCode` picks for the status code, such as `InvalidData` for 400, `AuthenticationError` for 401 and 403, and `ObjectNotFound` for 404, which also makes the record ignorable.

A result carries `StatusCode`, `RequestUrl`, `IsError`, and `Error`, and `SonarrClientResult<T>` adds `Value`, which isn't `null` when `IsError` is `false`. `IsIgnoreable` is `true` for a status below 400 and for 404. A result that `SonarrClientResult.FromException` builds takes the status code and the category its caller passes, and the caller passes `ErrorHandler.NoResponseCode`, 600, when there's no response. Both overloads hand a `SonarrHttpException` to an overload of their own, whose record also carries the exception's status code, reason phrase, headers, and request URL, and is ignorable for a 404.

## The sending cmdlet

The handlers reach the cmdlet that sent a request, an `IApiCmdlet`, through the request's options, where the client that sends the request puts it.

- Every cmdlet runs in a DI scope of its own, and the container gives each scope one `ApiCmdletAccessor`, in `src/MG.Sonarr.Next/Services/Http/`. `CmdletContextExtensions.CreateScope` and `SetContext`, which create the scopes of `SonarrCmdletBase` cmdlets and of `Connect-SonarrInstance`, set the accessor's `Cmdlet` to the cmdlet when it's an `IApiCmdlet`, and leave it `null` otherwise.
- `SonarrHttpClient` and `SonarrDownloadClient` take the accessor of the scope that resolves them, and each of their methods calls `AttachTo` before it sends, which stores the cmdlet in the request's options. The handlers read it back with `ApiCmdletAccessor.TryGetCmdlet`. The scoped `CommandTracker` and `TestingService` resolve the client from the same scope, so their requests reach the cmdlet too, and a request from a scope without a cmdlet, such as one that `Get-SonarrCommandHistory` sends, writes no verbose or debug output.
- Each request carries the cmdlet of the scope that sent it, so cmdlets that run at once, as in the runspaces of `ForEach-Object -Parallel` or in thread jobs, each get the output of their own requests only.
- `TimedCmdlet.WriteVerboseAfter` reports the time since the cmdlet last started its timer. The `Send*Request` helpers on `SonarrApiCmdletBase` start it, and a `TimedCmdlet` that calls a client or a service itself, as `Test-SonarrResource` and `Invoke-SonarrRssSync` do, starts it before each request.
- The handlers call the cmdlet's write methods on the thread that sent the request, which for a cmdlet is its pipeline thread, so an `IApiCmdlet` writes through its own `WriteVerbose` and `WriteDebug`, whose lines reach the verbose and debug streams, where redirection captures them and a transcript records them. Off the pipeline thread, `Cmdlet.WriteVerbose` throws a `PSInvalidOperationException` (measured 2026-10-25 on PowerShell 7.6.9), so nothing sends a cmdlet's request from another thread. A write throws a `PipelineStoppedException` under a `Stop` preference, or when the user halts the cmdlet at an `Inquire` prompt, and the handlers and the clients let it through.

## Download client

`ISonarrDownloadClient`, in `SonarrDownloadClient.cs`, saves a file that Sonarr serves, such as a backup or a log file, to a path. `AddSonarrClient` registers it as well.

- Its handler chain is `VerboseHandler`, `DebugSerializeHandler`, and `AuthHandler`, in that order, in front of a primary handler that `SonarrClientHandler.Configure` sets up, as the API client's is. It has no `PathHandler`, so the client itself puts the URL base in front of a relative download URL, or in place of the URL's own spelling of it when the URL starts with the base already, in any case. Sonarr gives a backup's `path` without the URL base and a log file's `downloadUrl` with it, in its own spelling, and Sonarr v3 lowercases the base (read in Sonarr's source on its `v3` and `main` branches, 2026-10-29). The URL that results is rooted, so combining it with the base address keeps only the address's scheme and server, and an absolute URL goes out unchanged.
- The download client and `AuthHandler`'s login spell the URL base with `ConnectionSettingsExtensions.GetUrlBase()`: as `IConnectionSettings.ServerUrlBase` spells it when that matches the path of `IConnectionSettings.ServiceUri` without regard to case, and as the connection's URL does otherwise, as behind a reverse proxy that maps one path to another, or before a test stored the server's. Sonarr serves `/backup/...` and `/logfile/...` only under its UI authentication, which the API key doesn't satisfy: under forms authentication, a request with only the key gets a 302 to `<base>/login` (measured 2026-11-14 against Sonarr 4.0.20.3014 in the sandbox). The forms login's cookie takes the URL base as its path, spelled as the login's request spelled it on Sonarr v4 (measured 2026-11-14 against Sonarr 4.0.20.3014 in the sandbox) and as Sonarr's own lowercased setting on v3 (read in Sonarr's source on its `v3` branch, 2026-11-14), and `CookieContainer` matches a cookie's path in case too (measured 2026-11-14 on .NET 11.0.0). So the login and every download spell the base the same way, the server's, or a download spelled otherwise goes out without the cookie and lands on the login page.
- A response whose status isn't a success becomes an error result, whose `SonarrHttpException` says that the server didn't return the file, with the category that the status calls for, and the client writes nothing, since the body of such a response, often an HTML page, isn't the file.
- No failure leaves the client as an exception, though a `PipelineStoppedException` from the cmdlet's own output does, as it does from `SonarrHttpClient`. A failure in `AuthHandler` gives `AuthenticationError`; a send with no response gives `ConnectionError`, `OperationTimeout` for a timeout, and `OperationStopped` for a cancellation; and an empty body, or a file that can't be written, such as one in a folder that doesn't exist, gives `WriteError`, whose record names the file's path as its target when writing failed.
- `AuthHandler` adds credentials when `IConnectionSettings.AuthType` says the server needs them, which `SendTest`, or `Connect-SonarrInstance -PassThru`, stored. It takes them from an `AuthedRequestMessage`, whose `Credentials` the download overload with a `NetworkCredential` sets, and which are `null` for a download without them.
	- A download without credentials goes out as it is, since Sonarr serves a client whose address its "Disabled for Local Addresses" setting exempts without a login, while its status still reports `forms` or `basic` (measured 2026-11-14 against Sonarr 4.0.20.3014 in the sandbox, which sees the host's requests come from a private address). When Sonarr answers it with a 401, as a Basic server does, or sends it to the login page, as a forms server does with a 302 that the primary handler follows to the page's 200, the handler fails it with a `SonarrHttpException`, so the login page never reaches the file.
	- For Basic authentication, it adds an `Authorization: Basic` header, encoded in a stack or pooled buffer that it clears afterward. Sonarr answers wrong credentials with a 401 (measured 2026-11-14 against Sonarr 4.0.20.3014 in the sandbox), and the handler fails such a request with the message that a forms login with wrong credentials gives, "The username or password is incorrect."
	- For forms authentication, it posts the credentials to the login page, `<base>/login?returnUrl=<base>/`. The primary handler follows the redirect that answers the login and keeps the login's cookie in the shared `CookieContainer`, which adds it to every later request. Sonarr redirects a login that it turns away to a URL with `loginFailed=true`, and one that it takes to the URL base, which it serves only to a request that carries the cookie, so a login that ends with an error status or anywhere on the login page failed. The handler logs in only when the container holds no cookie for the request's URL, so a download after a login in the same connection carries the session's cookie, whatever credentials it was given. When Sonarr answers a request with a 401 or sends it to the login page, the handler logs in again and resends the request once, to its original URL.
	- Sonarr sends a request to its login page only under forms authentication, which ignores a Basic header, so a download that lands there under `None` or `External`, or with Basic credentials, means that Sonarr's authentication changed after the connection's test stored the type (measured 2026-11-14 against Sonarr 4.0.20.3014 in the sandbox, from Basic, None, and External to forms). The handler fails such a download with a message that says to run `Connect-SonarrInstance` again, whose test stores the current type, so the page never reaches the file. Under `None` and `External`, a 401 goes on to the download client as it is, since under `External` it can come from a reverse proxy in front of Sonarr, which a new connection doesn't get past.
	- Every failure for want of a login reports the status 401, which the handler sets on a response that ended on the login page's 200 before the exception copies it.
- `Save-SonarrBackup` and `Save-SonarrLogFile` build their `NetworkCredential` from `-Credential` with `PSCredentialExtensions.ToLoginCredential()`, from the credential's own user name, since `PSCredential.GetNetworkCredential()` splits a domain off at a backslash, or at an `@` with no dot after it, and a login sends only the user name. `[ValidateLoginCredential]` turns away a credential with a blank user name or an empty password when the arguments bind, and `$null` and `[PSCredential]::Empty` mean no credentials.
